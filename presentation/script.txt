[Slide 5] HTTP는 보통 클라이언트가 시작한다
Approx. time: 3 min (12:00–15:00)

Intended slide content:
- Client ─ Request → Server ─ Response → Client
- “Client initiated” 표시
- Question: “B가 요청하지 않았으면 서버는?”

Say:
- 일반 HTTP 요청-응답에서는 클라이언트가 요청을 시작하고 서버가 응답합니다.
- 로그인, 조회, 상품 목록처럼 사용자가 필요할 때 가져오는 기능에는 매우 자연스럽습니다.
- 하지만 B가 아무 요청도 보내지 않는 동안 A가 움직이면, 평범한 요청-응답만으로는 B에게 새 상태를 보낼 계기가 없습니다.

Transition:
“가장 직관적인 첫 해결책은 B가 주기적으로 물어보는 것입니다.”

[Slide 6] 가장 단순한 해결: HTTP Polling
Approx. time: 3 min (15:00–18:00)

Intended slide content:
- `setInterval(fetchState, 100);`
- Client ─ GET /state → Server ─ state → Client (repeated)
- “변화가 없어도 요청한다”

Say:
- Polling은 클라이언트가 일정 간격으로 “상태가 바뀌었나요?”라고 HTTP 요청을 반복하는 방식입니다.
- 구현이 단순하고, 기존 HTTP API와 운영 도구를 그대로 활용하기 쉽습니다.
- 다만 새 변화가 없을 때도 요청과 응답이 계속 생깁니다.

Transition:
“그 간격 하나가 반응성과 요청량을 동시에 결정합니다.”

[Slide 7] Polling 간격은 지연과 요청 수의 교환이다
Approx. time: 4 min (18:00–22:00)

Intended slide content:
- 1000 ms: 적은 요청 / 눈에 띄는 지연
- 500 ms: 중간
- 100 ms: 더 빠른 반영 / 많은 요청
- Axis: polling interval ↓ → expected waiting time ↓, request frequency ↑

Say:
- Polling에서는 변화가 일어난 직후 다음 poll까지 기다려야 할 수 있습니다.
- 간격을 짧게 하면 평균적으로 더 빨리 보이지만 요청 빈도는 높아집니다.
- 실제 체감과 서버 부담은 네트워크, 응답 크기, 사용자 행동에 따라 달라지므로 이 슬라이드는 방향을 설명하는 것입니다.

Transition:
“간단한 수로 요청 패턴을 계산해 보겠습니다.”

[Slide 8] 20명이 100 ms마다 물으면?
Approx. time: 3 min (22:00–25:00)

Intended slide content:
- `20 clients × (1 / 0.1 s) = about 200 state requests/s`
- Small note: “상태 요청만의 단순 계산, 벤치마크 아님”

Say:
- 100 ms는 클라이언트 하나당 초당 약 10회의 상태 요청입니다.
- 20명이면 상태 요청만 대략 초당 200회가 됩니다. join, move, leave 요청은 별도입니다.
- 이 숫자는 이론적 예시일 뿐 성능 측정 결과가 아닙니다. 뒤에서 실제 서버의 카운터를 봅니다.

Transition:
“HTTP 안에서도 요청을 덜 반복하려는 두 가지 중간 해법이 있습니다.”

[Slide 9] Long Polling: 응답을 바로 끝내지 않는다
Approx. time: 2 min (25:00–27:00)

Intended slide content:
- Client ─ request → Server [wait for change / timeout] ─ response → Client
- Client immediately issues the next request

Say:
- Long Polling에서는 클라이언트가 요청한 뒤 서버가 변화, 타임아웃 등의 시점까지 응답을 보류합니다.
- 변화가 오면 응답하고, 클라이언트는 다음 요청을 새로 만듭니다.
- 일반 Polling보다 빈 요청을 줄일 수 있지만, 여전히 응답 후 다음 HTTP 요청을 다시 만드는 흐름입니다.

Transition:
“서버에서 클라이언트로 단방향 이벤트를 보내는 SSE도 있습니다.”

[Slide 10] SSE: 서버에서 클라이언트로 흐르는 스트림
Approx. time: 3 min (27:00–30:00)

Intended slide content:
- Polling: client repeatedly asks
- Long Polling: request waits, then reconnects
- SSE: Server → Client stream
- WebSocket: Client ↔ Server

Say:
- SSE는 서버에서 클라이언트로 이벤트를 보내는 단방향 스트림에 적합한 선택지입니다.
- 지금 게임은 클라이언트도 이동을 서버에 지속적으로 보내야 하므로, 양방향 통신 모델을 보려 합니다.
- 이 세 가지를 깊게 비교하는 시간이 아니라, WebSocket이 어떤 문제를 바꾸는지 위치를 잡는 슬라이드입니다.

Transition:
“이제 서버와 클라이언트가 계속 열어 두는 양방향 연결을 보겠습니다.”

[Slide 11] WebSocket은 Polling을 감춘 것이 아니다
Approx. time: 2 min (30:00–32:00)

Intended slide content:
- “One persistent connection”
- Client ↔ Server, client and server can each send frames when needed
- “not repeated HTTP GET /state”

Say:
- WebSocket은 HTTP Polling을 내부에 숨긴 기능이 아닙니다.
- 연결을 한 번 수립한 뒤 지속하고, 필요한 때 양쪽이 WebSocket frame을 보냅니다.
- 따라서 서버는 새 HTTP 상태 요청을 기다리지 않고도 연결된 클라이언트에 메시지를 보낼 수 있습니다.

Transition:
“그렇다고 처음부터 완전히 다른 연결로 시작하는 것은 아닙니다.”

[Slide 12] 시작은 HTTP Upgrade handshake다
Approx. time: 2 min (32:00–34:00)

Intended slide content:
- Client ─ HTTP Upgrade → Server
- Server ─ 101 Switching Protocols → Client
- Then: persistent WebSocket connection

Say:
- WebSocket 연결은 보통 HTTP Upgrade 요청과 `101 Switching Protocols` 응답으로 시작합니다.
- 그 뒤 같은 TCP 연결 위에서 WebSocket protocol의 frame을 주고받습니다.
- WebSocket이 TCP를 없애는 것이 아니라 TCP 위에 놓이는 프로토콜이라는 점을 구분해 두겠습니다.

Transition:
“Upgrade 이후에는 어떤 메시지가 오갈까요?”

[Slide 13] 연결을 유지하며 WebSocket frame을 주고받는다
Approx. time: 2 min (34:00–36:00)

Intended slide content:
- Persistent TCP connection
- Browser A `MOVE` frame → server
- server `STATE` frame → A/B/C
- Full duplex label

Say:
- 클라이언트는 이동할 때 MOVE를 보내고, 서버는 상태가 바뀌면 STATE를 보냅니다.
- full-duplex는 양쪽 모두 같은 지속 연결에서 보낼 수 있다는 의미입니다.
- 이것이 “서버가 B에게 어떻게 알리는가”에 대한 통신 모델의 답입니다.

Transition:
“여기서 자연스럽게 또 하나의 질문이 생깁니다. 서버는 메시지가 올 때까지 무엇을 하나요?”

[Slide 14] `while True`면 서버가 계속 확인하는 것 아닌가?
Approx. time: 2 min (36:00–38:00)

Intended slide content:
```python

```
- Question: “이것도 polling인가?”

Say:
- 코드의 `while True`만 보면 반복 확인처럼 보일 수 있습니다.

- 핵심은 `await`입니다. 데이터가 없으면 이 coroutine은 기다리는 동안 실행을 양보합니다.

[Slide 15] `await receive_json()`은 busy polling이 아니다
Approx. time: 3 min (38:00–41:00)

Intended slide content:
- `await websocket.receive_json()`
- current coroutine suspends → event loop can run other work → data arrives → coroutine resumes
- “No repeated application-level HTTP request”

Say:
- `await websocket.receive_json()`은 소켓에 JSON 메시지가 도착할 때까지 현재 coroutine을 suspend합니다.
- 그 시간에 event loop는 다른 연결이나 다른 작업을 처리할 수 있습니다.
- 데이터가 도착해 읽을 수 있게 되면 기다리던 coroutine이 다시 실행됩니다.
- 그러므로 이것은 CPU가 계속 소켓을 확인하는 busy waiting도, 클라이언트가 HTTP GET을 계속 보내는 HTTP Polling도 아닙니다.

Transition:
“이 기다림을 가능하게 하는 층을 FastAPI부터 아래로 내려가 보겠습니다.”

[Slide 16] FastAPI 아래에서 기다림이 이어지는 층
Approx. time: 3 min (41:00–44:00)

Intended slide content:
- FastAPI application
  ↓ ASGI / Uvicorn
  ↓ async event loop
  ↓ OS socket / I/O readiness mechanism
  ↓ TCP connection

Say:
- 애플리케이션에서 `await`를 쓰면 FastAPI 코드만으로 모든 I/O를 구현하는 것은 아닙니다.
- ASGI 서버인 Uvicorn과 async event loop가 소켓 I/O를 연결하고, 아래에서는 운영체제가 소켓의 읽기 가능 상태를 알려 줍니다.
- 이 그림은 구현 세부를 모두 설명하려는 것이 아니라, 기다림이 어느 층에서 일어나는지 정확하게 잡기 위한 것입니다.

Transition:
“리눅스에서 자주 듣는 epoll은 이 그림의 어디에 있을까요?”

[Slide 17] epoll은 HTTP Polling과 다른 층의 말이다
Approx. time: 3 min (44:00–47:00)

Intended slide content:
- Async event loop → OS I/O readiness mechanism → socket readable
- “Linux에서는 epoll 같은 I/O multiplexing mechanism이 사용될 수 있음”
- “epoll의 poll ≠ HTTP Polling”

Say:
- Linux 환경에서는 event loop/runtime 구성에 따라 epoll 같은 I/O multiplexing mechanism이 아래 계층에서 사용될 수 있습니다.
- FastAPI가 epoll을 직접 구현한다고 말하면 정확하지 않습니다. FastAPI, ASGI/Uvicorn, event loop, OS의 역할을 분리해서 봐야 합니다.
- epoll이라는 이름의 `poll`도 HTTP Polling과 같은 뜻이 아닙니다. 여기서는 많은 소켓의 준비 상태를 효율적으로 통지받는 OS 수준의 메커니즘을 가리킵니다.

Transition:
“이제 추상적인 흐름을 우리가 방금 시연한 실제 코드에 연결하겠습니다.”

[Slide 18] 실제 WebSocket 서버: 연결 → 상태 변경 → broadcast
Approx. time: 3 min (47:00–50:00)

Intended slide content:
- Browser `join` / `move` → `/ws` → in-memory `players` → `broadcast_state()` → all `active_connections`
- Short source excerpts: `await websocket.accept()`, `data = await websocket.receive_json()`, `await broadcast_state()`
- Message schemas: join `{type, name}`, move `{type, x, y}`, state `{type, players}`

Say:
- 실제 앱은 `/ws`와 proxy-friendly `/websocket/ws`를 같은 WebSocket endpoint에 연결합니다. public frontend는 `/websocket/ws`를 사용합니다.
- 서버는 connection별로 server-generated player ID를 연결해 두고, 클라이언트가 보낸 player ID는 신뢰하지 않습니다.
- join과 move 뒤에는 `broadcast_state()`가 현재 `players` 목록을 모든 active connection에 보냅니다. disconnect 뒤에도 같은 broadcast가 실행됩니다.

Source for PDF snippets:
- websocket-server/app.py:75–82: `broadcast_state()` payload와 `send_json` loop
- websocket-server/app.py:85–131: `/ws`·`/websocket/ws`, accept, receive, join/move, disconnect
- websocket-server/static/game.js:24–35 and 91: WebSocket open/message and join/move sends

Transition:
“다음 27분 동안은 이 broadcast를 직접 완성해 보겠습니다.”
